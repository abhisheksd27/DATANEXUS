§1 — Business Problem Statement

1.1 Executive Summary

Modern e-commerce enterprises such as Amazon, Flipkart, Swiggy, and Zomato process millions of transactions and user interactions every single second. Their infrastructure is built on microservices — each service owns its own isolated database.

The critical engineering challenge: all of this data sits in silos. The Orders service uses MySQL. The User service uses PostgreSQL. Customer behaviour streams through Kafka. Market data lives behind REST APIs. There is no single place to ask cross-domain questions.

🚨 The Core Problem A business analyst cannot answer: "How does heavy rain in Mumbai affect high-value order delivery timelines and today's revenue?" — because the weather data, order data, delivery data, and user data all live in completely different systems.

1.2 Five Technical Problems We Are Solving

#ProblemTechnical CauseBusiness Impact
1Data SilosOrders in MySQL, Users in PostgreSQL, Events in Kafka, External data in APIsCannot compute cross-domain analytics
2Analytical LatencyRunning GROUP BY queries on production OLTP databases causes table locksStale 24-hour-old reports, slow app performance
3Lost Streaming SignalsClickstream events (page views, cart adds) happen at millisecond frequency — RDBMS cannot ingest themMissed real-time recommendations, high cart abandonment
4Data Quality DegradationMicroservices emit null fields, negative amounts, or malformed emails without validationIncorrect KPIs, corrupted financial dashboards
5Infrastructure DriftManual cloud resource creation diverges between dev, staging, and production environmentsDeployment failures, uncontrolled cloud costs

1.3 Strategic Objectives

  • Zero Operational Disruption: Ingest database changes via CDC without touching or locking production databases
  • Sub-Minute Streaming: Process clickstream events continuously with less than 60 seconds end-to-end latency
  • Unified Data Lake: Consolidate all sources into Bronze → Silver → Gold Medallion layers on GCS
  • Modern ELT Warehouse: Star Schema dimensional models in BigQuery using dbt
  • Automated Quality Gates: No data flows into BigQuery without passing Great Expectations validation
  • Infrastructure as Code: Everything provisioned via Terraform — reproducible in under 5 minutes

§2 — System Architecture Overview

2.1 Architecture Philosophy

DataNexus follows a Lambda Architecture pattern — combining a batch processing layer (for accuracy and historical data) with a streaming layer (for real-time event processing). Both layers write into the same unified Medallion Data Lake.

3.1 MySQL — Orders OLTP Database

MySQL is a relational database management system (RDBMS) storing data in structured rows/columns. In DataNexus it simulates the Orders microservice database containing orders, order_items, and payments tables. Configured with Binary Log in ROW format so Debezium can read each row change without querying tables.

3.2 PostgreSQL — Users & Inventory OLTP Database

PostgreSQL is an advanced RDBMS supporting JSON, arrays, and complex types. Simulates the Users and Inventory microservices with users and inventory tables. Configured with WAL Logical Replication so Debezium can stream changes via logical decoding.

3.3 Apache Kafka — The Event Streaming Backbone

Kafka is a distributed event streaming platform capable of handling millions of events per second. Core concepts:

ConceptWhat It IsAnalogy
ProducerApplication that writes eventsReporter filing a story
TopicNamed channel/category of eventsNewspaper section
PartitionTopic split for parallel processingMultiple printing presses
ConsumerApplication that reads eventsReader subscribing to section
OffsetUnique sequential ID per eventPage number in newspaper
Consumer GroupMultiple consumers sharing loadMultiple readers splitting sections

3.4 Debezium — Change Data Capture (CDC)

Debezium is a CDC tool that reads database transaction logs (MySQL Binary Log, PostgreSQL WAL) and publishes every INSERT/UPDATE/DELETE as a Kafka event — in real time, without querying tables, without locking, without degrading database performance.

Why CDC instead of polling? Polling (running SELECT every 5 seconds) is slow, misses deletes, stresses the database, and creates duplicate records. CDC reads the internal transaction log — capturing every atomic change instantly.

3.5 Apache Spark — Distributed Processing Engine

Spark is a distributed in-memory data processing framework. It splits data into partitions and processes them in parallel across many CPU cores or machines. Two modes used in DataNexus:

  • Spark Batch (ETL): Reads GCS Bronze → cleans/joins → writes GCS Silver → Gold → BigQuery
  • Spark Streaming: Reads Kafka events continuously in micro-batches → writes to GCS Bronze in real time

3.6 Apache Airflow — Workflow Orchestration

Airflow is a platform for authoring, scheduling, and monitoring data pipelines as code. Pipelines are defined as DAGs (Directed Acyclic Graphs) — Python files where each node is a task and edges define dependencies.

# Example Airflow DAG concept
ingest_api >> spark_bronze_etl >> spark_silver_etl >> spark_gold_etl >> bq_load >> dbt_run >> quality_check

3.7 Google Cloud Storage — Data Lake

GCS is Google's object storage — a virtually unlimited cloud hard drive. In DataNexus it hosts the Medallion Data Lake with three zones: Bronze (raw), Silver (cleaned Parquet/Delta Lake), and Gold (aggregated, join-ready datasets).

3.8 Google BigQuery — Analytical Data Warehouse

BigQuery is a serverless, fully-managed analytical warehouse. It runs petabyte-scale SQL queries in seconds using distributed columnar storage. It is the final destination for processed data — where analysts and dashboards query from.

FeatureData Lake (GCS)Data Warehouse (BigQuery)
FormatRaw files (JSON, Parquet)Structured tables
Query methodCode (Spark/Python)SQL directly
UsersData EngineersData Analysts, BI Tools
SpeedSlower (file scanning)Very fast (columnar, cached)

3.9 dbt — ELT Transformation Framework

dbt (data build tool) turns SQL SELECT statements into managed tables/views inside BigQuery. It handles dependency resolution, test assertions, and documentation automatically — making SQL transformations version-controlled and testable.

3.10 Terraform — Infrastructure as Code

Terraform lets you define cloud infrastructure in code files (.tf). Running terraform apply creates all GCP resources (GCS buckets, BigQuery datasets, IAM roles) automatically — reproducible in any environment.

3.11 Docker & Docker Compose — Containerization

Docker packages software into self-contained, portable containers. Docker Compose orchestrates multiple containers together. Used for local development — one docker-compose up -d boots MySQL, PostgreSQL, Kafka, Zookeeper, Spark Master, and Spark Worker simultaneously.

3.12 Great Expectations — Data Quality

Great Expectations is a Python library for automated data validation. You define "expectations" (rules) such as "order_id must never be null" or "total_amount must be > 0". It validates data at every zone boundary and blocks bad records from proceeding.

§4 — Medallion Architecture & Pipeline Flows

4.1 Medallion Architecture Explained

Used at Netflix, Uber, and Databricks — the Medallion (Bronze/Silver/Gold) architecture organizes data into three progressively refined zones:

ZoneNicknameContentFormatWho WritesWho Reads
BronzeRawExact copy of source data. Nothing changed. Immutable.JSON, CSVDebezium, Spark Streaming, API IngestorSpark Silver ETL
SilverCleanedDeduplicated, nulls handled, dates standardizedParquet (Delta Lake)Spark Bronze→Silver ETLSpark Gold ETL
GoldBusiness-ReadyMulti-table joins, aggregations, enriched with weather/currency dataParquet (Delta Lake)Spark Silver→Gold ETLBigQuery Loader

4.3 Batch Pipeline Flow (ETL)

1

Airflow DAG Triggers at Midnight

Scheduler fires the daily_etl_pipeline DAG at 00:00

2

API Ingestor Runs

Python scripts call OpenWeatherMap & Exchange Rate APIs → save JSON to GCS Bronze

3

Debezium Streams CDC Events

MySQL binlog + PostgreSQL WAL changes flow through Kafka → Spark Streaming writes to GCS Bronze

4

Spark Bronze→Silver ETL

PySpark reads Bronze JSON → deduplicates, type-casts, standardizes → writes Parquet to Silver

5

Spark Silver→Gold ETL

Joins orders + users + inventory + weather → calculates daily revenue, delivery SLAs → writes Gold

6

BigQuery Load

Gold Parquet files loaded into datanexus_raw BigQuery dataset

7

dbt Runs Transformations

Staging → Fact/Dim models → Aggregations built inside BigQuery

8

Dashboards Refresh

Grafana & Looker Studio display updated revenue, orders, user behavior KPIs

4.4 Streaming Pipeline Flow (Real-Time)

1

User Action on Website

Customer clicks a product page → frontend sends clickstream event

2

Kafka Producer Publishes

Event written to clickstream_events Kafka topic with full user/product context

3

Spark Streaming Reads Kafka

Micro-batch job reads clickstream_events every 10 seconds

4

Enrich & Write to GCS Bronze

Events enriched with user data → written to GCS Bronze partitioned by hour

5

Real-Time Aggregation

Trending products counted per minute → written to BigQuery streaming buffer

6

Grafana Dashboard Updates

Real-time product trends visible every 30 seconds

§6 — Implementation Roadmap (10 Steps)

STEP 1

Local Development Infrastructure (Docker)

Set up MySQL, PostgreSQL, Kafka, Zookeeper, Spark Master, Spark Worker — all in Docker containers on a shared bridge network. Configure MySQL binlog and PostgreSQL WAL for future CDC ingestion.

STEP 2

Cloud Infrastructure as Code (Terraform + GCP)

Provision GCS Data Lake bucket (Bronze/Silver/Gold folders), BigQuery datasets (raw, staging, analytics), and IAM Service Accounts using Terraform. No manual console clicks.

STEP 3

Multi-Source Data Ingestion (Debezium + Kafka + API)

Configure Debezium CDC connectors for MySQL and PostgreSQL. Write Python Kafka producers for clickstream events. Write API ingestors for OpenWeatherMap and Exchange Rate APIs.

STEP 4

Batch Processing ETL Pipeline (PySpark)

Write PySpark jobs to transform Bronze → Silver (clean, deduplicate, type-cast) and Silver → Gold (join, aggregate, enrich). Output: Parquet files stored in Delta Lake format on GCS.

STEP 5

Real-Time Streaming Pipeline (Spark Structured Streaming)

Write Spark Structured Streaming jobs that consume Kafka clickstream events continuously, enrich them, and write to GCS Bronze in real time using micro-batch processing.

STEP 6

Data Warehouse & ELT (BigQuery + dbt)

Load Gold Parquet files into BigQuery. Build dbt SQL models: staging models → fact_orders → dim_users → agg_daily_revenue. Implement Star Schema dimensional modeling.

STEP 7

Pipeline Orchestration (Apache Airflow)

Build Airflow DAGs connecting all tasks in order with dependency management, retry logic, and failure alerts. The main DAG: API Ingest → Spark ETL → BigQuery Load → dbt → Quality Check.

STEP 8

Data Quality Framework (Great Expectations)

Write expectation suites for each data zone boundary. Automate validation gates so corrupted or incomplete data is blocked from proceeding to Silver/Gold/BigQuery.

STEP 9

REST API Serving Layer (FastAPI)

Build a FastAPI application with endpoints: /api/v1/revenue/daily, /api/v1/revenue/by-city, /api/v1/products/trending, /api/v1/delivery/sla. Deploy on GCP Cloud Run via Dockerfile.

STEP 10

Business Dashboards (Grafana + Looker Studio)

Configure Grafana for pipeline operational metrics (Kafka lag, Spark job times, Airflow DAG health). Connect Looker Studio to BigQuery for business KPI dashboards (Revenue, DAU, Delivery SLA).
